## 固定條件與量測邊界

- macOS ARM64、CPython 3.14.5、Tcl/Tk 9.0.3。使用實際 AniCat GUI；受控階段事件是診斷刺激，不計入真站下載驗收。
- 前景由 AppKit 僅在本次自有測試 PID 間控制，獨立程序以同步 Process Manager API 每約 250ms 記錄前景 PID、CPU，並持續做 20ms 計時。失焦／工作程序提前退出／CPU 不符的輪次保留並排除，沒有把等待前景的時間計入。
- CPU 匹配實驗：8 個 CPU 工作程序，或 2 個 CPU 工作程序加 2 個持續 FFmpeg 解碼工作。每輪先暖機 1.5 秒，再量 12 秒；至少 90% CPU 樣本須 >=95%，三輪正反交錯。比較的是實測總 CPU 飽和條件，沒有停止使用者其他 Apps 或修改全域設定。
- 同一程序內依序切換原始寬度／固定寬度，字型、內容、工作量相同。兩列每 500ms 切換真實階段文字，記錄 callback 與其後 `update_idletasks` 的分開耗時；後者包含延後的幾何與繪製工作。這個強制 flush 只用於診斷，產品與真站驗收沒有加入它。
- 診斷解碼程序依固定時間結束，只作負載；完整下載與全片解碼的通過標準另見真站驗收。

前後兩輪各下載兩部，均實際從 mapped widget 讀到「解析來源 → 下載中 → 檢查分段 → 合併影片 → 全片驗證 → 完成」，最後顯示 2 / 2。AES 來源 402 段全加密；明文 614 段全部下載及驗證。固定 badge 另以實際字型量測確認所有狀態文字放得下（可用 56px，最長狀態 46px）。兩部前後的 manifest hash 與完整輸出 SHA256 均相同。

獨立全片解碼指令：`ffmpeg -nostdin -v error -xerror -i <output> -fps_mode passthrough -enc_time_base demux -f null -`。這不是只 probe、Range smoke 或抽樣解碼。兩輪的網路時序、階段重疊與平均總 CPU 不完全相同，不把單次真站最大值差異當成嚴格因果百分比；上面的 CPU 匹配交錯測試才是修正取捨依據。

合併期間的既有可恢復 AAC 時間戳修正逐筆保存於各 FFmpeg job；完整解碼的 stderr 空白不表示合併階段零 warning。所有 fatal 診斷仍拒絕該嘗試，未新增忽略規則。
